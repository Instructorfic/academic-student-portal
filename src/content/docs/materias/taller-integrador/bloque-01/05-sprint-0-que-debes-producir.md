Todo lo estudiado en este bloque se aplica directamente en tu Sprint 0,
donde tu equipo:

1. se conforma y asigna roles iniciales
2. crea su repositorio Git con README inicial
3. define su Objetivo de producto y su Product Backlog inicial
4. establece una Definition of Done inicial
5. esboza una arquitectura inicial
6. deja funcionando un ambiente de desarrollo para todo el equipo.

## Por qué importa hacerlo en este orden

Cada uno de estos seis puntos depende del anterior: no tiene sentido
esbozar una arquitectura antes de tener un Product Backlog (¿arquitectura
para construir qué?), ni definir roles después de empezar a programar
(¿quién decide qué se prioriza?). Sprint 0 existe precisamente para
que este orden no quede a la improvisación de la primera sesión de
código.

## Definition of Done inicial

Para este primer incremento se utiliza una definición sencilla, que
evolucionará conforme avance el proyecto:

```text
☐ Está implementado
☐ Puede ejecutarse
☐ Cumple los criterios de aceptación
☐ No presenta errores evidentes
☐ Está incorporado al repositorio
```

## Sprint 0 no significa construir todo el sistema

El objetivo no es terminar el producto. Es llegar a un punto donde el
equipo pueda comenzar a desarrollar con claridad:

```text
Proyecto definido → Equipo organizado → Backlog inicial → Repositorio
        ↓
Aplicación funcionando → Primer incremento → Sprints de desarrollo
```

**Error común:** intentar que el "primer incremento" de Sprint 0 sea ya
una funcionalidad completa y pulida del proyecto. No lo es: es la
demostración mínima de que el equipo puede llevar una historia de
usuario, de principio a fin, desde el Product Backlog hasta código que
se ejecuta. La calidad y el alcance de las funcionalidades reales llegan
en los sprints posteriores del taller.

## Cuándo se considera cerrado Sprint 0

Sprint 0 se considera cerrado cuando tu equipo puede ejecutar
localmente un esqueleto mínimo del sistema y cuenta con un Sprint
Backlog para el primer sprint de desarrollo. A partir de ese esqueleto
construirás, en los siguientes bloques, tu primer incremento funcional
real del proyecto.

## Para reflexionar

- Si tu equipo tuviera que demostrar Sprint 0 mañana mismo, ¿qué de la
  lista de seis puntos todavía falta?
- ¿Tu Definition of Done inicial es lo suficientemente concreta para
  que dos integrantes distintos lleguen a la misma conclusión sobre si
  una historia está "terminada"?

## Evidencia esperada

Al cerrar Sprint 0 debes tener, como evidencia: roles Scrum asignados,
definición del proyecto (problema, usuarios, alcance, restricciones),
Product Backlog con al menos 6 historias, repositorio con README, y al
menos una funcionalidad ejecutable y demostrable.
